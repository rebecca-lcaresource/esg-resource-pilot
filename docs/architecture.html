Supplier ESG Register · System Architecture

How the tool is wired, end to end

A Tier-3 internal register where four roles hold different read and edit rights over the same supplier records. This page maps every moving part — the browser app, Supabase, the Brevo email path, and the one function still on the drawing board — and traces how data actually flows between them.

Component inventory

What each part is, and what it holds

Keys are noted where they live. The golden rule: the browser only ever holds public, RLS-bounded credentials; anything that can bypass security stays server-side.

Frontend

React app (browser)

Vite + Tailwind single-page app: sign-in, supplier register, role-aware detail view, user management, archive, CSV export. Talks to Supabase through the supabase-js client.

Holds: Supabase URL + anon key (public, browser-safe) and the signed-in user's JWT. Nothing privileged.
Hosting + CI

Netlify

Serves the static build on its CDN and rebuilds from GitHub main. Also the intended home of the scheduled digest function.

Env vars: VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY at build; SUPABASE_SERVICE_ROLE_KEY + BREVO_SMTP_* reserved for the digest fn.
Source

GitHub

The repository. A push to main triggers a Netlify build and deploy (currently kicked off manually while auto-deploy is being fixed).

Holds: code and docs only — never a key or secret value.
Database

Supabase Postgres

Three tables — profiles, suppliers, change_log — plus the suppliers_pc view. RLS on every table; triggers enforce column rules and write the audit log.

Enforces: who reads which rows and columns, who may edit which fields, and the append-only change log. This is the real security boundary.
Identity

Supabase Auth

Email one-time 8-digit code, invite-only, self-signup disabled. Sends codes through Brevo and issues a session JWT carrying the user id.

Config: Brevo SMTP credentials entered in the Auth dashboard (not an env var) so Auth can send login codes on the authenticated domain.
Email · external

Brevo SMTP

Outbound email relay on the authenticated lcaresource.com domain (smtp-relay.brevo.com:587). Two consumers: Supabase Auth (login codes) and the planned digest function.

Holds: SMTP login + key — stored in the Supabase Auth dashboard and (for the digest) in Netlify env vars. Never in the repo.
Planned · not built

Scheduled digest function

A Netlify scheduled function meant to run daily at 07:00 ET: read the last 24h of the change log, compose one digest, and send it — to admin, purchasing and sustainability only, never production control, and nothing at all on a day with no changes.

Would use: the service-role key (bypasses RLS) — which is exactly why it lives in a server function and never in the browser.
Data flow 01

Authentication — the login code

No password and no clickable link. Enterprise mail scanners consume single-use links before the recipient clicks, so the tool emails a code the user types in.

Why it needs the service-role key: to compose the digest it must read the change log across all users, which means bypassing RLS. That key is all-powerful, so it lives only in this server-side function — never in the browser, never in the repo. Production control is excluded because a digest would carry field changes they are not permitted to see.
Trust boundaries

Where every key lives — and what it can do

The browser is untrusted. The security boundary is Postgres RLS. Credentials are placed by that principle.

CredentialStored inUsed byPower
Anon / publishable key Browser build · Netlify env config Frontend Public and browser-safe. Every request is still bounded by RLS.
User session JWT Browser session browser Frontend Acts as one specific user — that user's role and nothing more.
Service-role key Netlify env · digest fn only server-only Planned digest function Bypasses all RLS. Never in the browser or any user-facing path.
Brevo SMTP login + key Supabase Auth dashboard; Netlify env for the digest config Supabase Auth · digest fn Sends email as the authenticated lcaresource.com domain.
!
The single rule that keeps the model honest: the service-role key never crosses into the browser. Everything a user touches goes through RLS; only the isolated server function is trusted to read across users.
